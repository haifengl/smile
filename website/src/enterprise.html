Why SMILE excels at the edge

A complete AI engine—train, score, and explain in place

  • Zero-dependency core (tiny footprint) For resource-constrained edge gateways, SMILE's core module is completely self-contained. It runs pure JVM-optimized bytecode with compact data structures—drastically outperforming Python or R in memory efficiency without requiring external native binaries.
  • Plug-and-play hardware acceleration Run pure Java on the CPU you already have, or drop in optional native dependencies when an edge node has a GPU or NPU: OpenBLAS/LAPACK for linear algebra, ONNX Runtime execution providers (CUDA, DirectML, NPU), and a LibTorch (PyTorch C++) backend for hardware-accelerated deep learning.
  • Built-in Classic ML, ONNX & LLM stack SMILE Serve hosts an OpenAI-compatible REST server and bundled React UI in a single process—serving serialized classical models (.sml decision trees, random forests, k-means, regressors), direct internal routing to .onnx models, and native local SLMs/LLMs with tokenizers, GQA, RoPE, and radix KV-caching.
  • On-device training & local adaptation Edge nodes do not just score static weights. Actively train and update Random Forests, Gradient Boosting, clustering, or anomaly detectors directly on edge data, and compute local TreeSHAP explanations right where the decision ran.
  • Explained where it ran Every classical ML decision can carry a local SHAP explanation (exact TreeSHAP for tree ensembles, LinearSHAP for linear models, and KernelSHAP for neural, SVM, discriminant, and Gaussian Process models) alongside posterior probabilities. The audit stays with the event, on the node.
  • Resilient & hot-reloadable offline Inference continues when the link is down. Updated .sml and .onnx models hot-swap atomically from disk or drain gracefully without restarting the process, backed by Kubernetes-ready health probes and unified Prometheus telemetry.

Architecture comparison

SMILE vs. ONNX Runtime / LiteRT

Depending on what your edge workload does, you can run SMILE standalone or pair its native ONNX routing with classical ML and local SLMs in a single process:

Feature / Goal ONNX Runtime / LiteRT SMILE Engine
Primary Use Case Deploying heavy deep learning models (YOLO, ResNet, BERT) trained elsewhere. End-to-end edge data science: feature engineering, classical ML, analytics, ONNX routing, and local LLMs.
On-Device Training Incredibly difficult; optimized almost exclusively for static inference. Supported natively. Actively train algorithms (Random Forests, Gradient Boosting, K-Means, DBSCAN) directly on edge data.
Dependencies & Footprint Typically deployed inside a bloated Python environment alongside bulky platform-specific native binaries—resulting in multi-GB footprints, high memory overhead, and poor real-time predictability on edge hardware. Pure Java by default (or a self-contained GraalVM native binary) with deterministic latency; native extensions (OpenBLAS, ORT, LibTorch) are completely optional.
Explainability External post-processing required; no built-in feature attribution. Built-in TreeSHAP & KernelSHAP computed in-process per inference request or SSE stream, with interactive Waterfall, Force, and Decision plots in the Web UI.
Serving & Operations C++/Python library; requires custom wrapper for REST, UI, or metrics. Turnkey Quarkus server (0.2 GB micro native image, 0.4 s boot, ~80 MiB idle RAM) with OpenAI-compatible API, React UI, and Prometheus metrics.
